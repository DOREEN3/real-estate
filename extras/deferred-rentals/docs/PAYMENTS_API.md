# Payments API

The payment workflow is based on the existing `payments`,
`payment_receipts`, `installments`, `rent_payments`, and
`rent_payment_receipts` tables in `database/real_estate (2).sql`. Sale and
rent payments remain separate ledgers. Every endpoint requires an admin
bearer access token because payment and receipt records contain financial
information.

## Sale payments

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/v1/admin/sales/{id}/payments` | Record a sale payment and issue a receipt |
| GET | `/api/v1/admin/sales/{id}/payments` | List payments for a sale |
| GET | `/api/v1/admin/payments` | Filter and list sale payments |
| GET | `/api/v1/admin/payments/{id}` | Retrieve a sale payment and receipt |
| PATCH | `/api/v1/admin/payments/{id}/status` | Confirm or fail a pending provider payment |

Example request:

```json
{
  "amount": "12500.00",
  "payment_type": "installment",
  "payment_method": "mobile_money",
  "payment_source": "manual",
  "transaction_reference": "TXN-100",
  "payment_date": "2026-11-05T10:30:00+03:00",
  "installment_id": 81
}
```

`amount`, `payment_type`, and `payment_method` are required.
`payment_source` is `manual` by default or may be `provider`;
`transaction_reference`, `payment_date`, and `installment_id` are optional.
Amounts must be positive values fitting `DECIMAL(15,2)`. Payment types and
methods are stored as supplied, up to 30 characters, because the database
defines these columns as `VARCHAR`, not an enum. Payment source and status are
always explicitly written: manual payments are `completed`, while provider
payments begin `pending`. For provider payments, `provider` is required and
`provider_reference` is optional; provider details are not accepted for
manual payments.

Completed payments alone count toward the sale balance. A deposit payment
must reference that sale's installment number 0. Payments on a scheduled sale
must be allocated to an installment; its status is updated only when the
payment is completed. All amounts are checked against the outstanding sale
balance, and against the installment balance when linked. The acting admin
populates `recorded_by` and `issued_by`; these fields cannot be supplied by
the caller.

Manual completed payments receive a receipt in the same transaction. A
provider payment is recorded as pending and does not change installment
status or create a receipt. The system does not call a payment provider.
After independently verifying the provider result, an admin resolves the
pending record:

```json
{
  "payment_status": "completed",
  "provider_reference": "MPESA-CONFIRMED-123"
}
```

`payment_status` must be `completed` or `failed`. Confirmation rechecks the
completed sale and installment balances; an over-balance result remains
pending and has no receipt. A failed provider payment has no receipt and does
not update installment status. Confirmed payments receive their receipt and
update the installment status atomically.

## Rent payments

| Method | Path | Purpose |
|---|---|---|
| POST | `/api/v1/admin/rent-charges/{id}/payments` | Record a rent payment and issue a receipt |
| GET | `/api/v1/admin/rent-charges/{id}/payments` | List payments for a rent charge |
| GET | `/api/v1/admin/rent-payments` | Filter and list rent payments |
| GET | `/api/v1/admin/rent-payments/{id}` | Retrieve a rent payment and receipt |

Rent-payment requests accept required `amount_paid` and `payment_method`, and
optional `transaction_reference` and `payment_date`. Amount validation and
date handling match sale payments. The rent charge must exist.

For either workflow, omitted `payment_date` defaults to the current server
time. Supplied ISO 8601 timestamps are converted to the configured application
timezone. Payment insert and receipt issuance happen in one database
transaction for completed manual or rent payments. Receipt numbers are
generated by the API and are unique. Pending or failed provider payments have
no receipt.

List endpoints are paginated (`page`, default 1; `limit`, default 12, maximum
100). Sale-payment filters: `sale_id`, `payment_type`, `payment_method`,
`payment_source`, and `payment_status`.
Rent-payment filters: `rent_charge_id` and `payment_method`.

The API records a financial ledger entry and issues its receipt; it does not
charge an external payment provider. Payments and receipts cannot be edited or
deleted through these endpoints. The API does not change sale or installment
records beyond updating installment status after a completed sale payment.
